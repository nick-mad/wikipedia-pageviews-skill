# wikipedia-pageviews: навичка AI-агента для дослідження інтересу до тем

Навичка у форматі [Agent Skills](https://agentskills.io/specification). З нею агент відповідає
засновникам B2C-продуктів на питання на кшталт «чи зростає інтерес до теми X у мовному
розділі Y і чи можна цьому вірити?» або «яку мову запускати наступною?». Відповіді
спираються на [Wikimedia Pageviews API](https://doc.wikimedia.org/generated-data-platform/aqs/analytics-api/reference/page-views.html).
Навичка будує графіки й збирає PDF-звіт на одну сторінку.

- Директорія навички: [`wikipedia-pageviews/`](wikipedia-pageviews/). Усе лежить у ній: `SKILL.md`, код, тести, evals, приклади.
- Приклади звітів: [`wikipedia-pageviews/examples/`](wikipedia-pageviews/examples/)
- Методологія: [`wikipedia-pageviews/references/methodology.md`](wikipedia-pageviews/references/methodology.md)

## Швидкий старт

Потрібен лише [`uv`](https://docs.astral.sh/uv/). Python і залежності він підтягне сам
з `uv.lock`, скомпільованих файлів у репо немає.

```bash
# підключити навичку до Claude Code (або будь-якого агента з підтримкою Agent Skills)
mkdir -p ~/.claude/skills && ln -s "$PWD/wikipedia-pageviews" ~/.claude/skills/wikipedia-pageviews

# або викликати CLI напряму
wikipedia-pageviews/scripts/wpv resolve "intermittent fasting" --langs pl,cs
wikipedia-pageviews/scripts/wpv analyze --topic "Intermittent fasting=Q1666254" --langs pl,cs
wikipedia-pageviews/scripts/wpv report wpv-output/intermittent-fasting_pl-cs --headline ... --summary ... --recommendation ...

# переглянути збережений приклад без мережі
wikipedia-pageviews/scripts/wpv show wikipedia-pageviews/examples/4-chess-followup

# тести (офлайн, на записаних відповідях API)
cd wikipedia-pageviews && uv run pytest
```

Змінна `WPV_CONTACT` задає контакт у User-Agent: політика Wikimedia вимагає вказувати
контакт. `WPV_CACHE_DIR` задає, де лежить кеш (за замовчуванням `~/.cache/wikipedia-pageviews`).

## Як це працює

```
запит користувача
   │
   ▼
SKILL.md ── короткий сценарій для агента: які команди, як читати результат, як відповідати
   │
   ├─ wpv resolve   тема → кандидати Wikidata (QID) + які мови мають статтю
   ├─ wpv analyze   QID × мови × період → analysis.json + chart.png + стислий підсумок у stdout
   ├─ wpv show      повторно показати збережений підсумок (без мережі)
   └─ wpv report    analysis.json + текст агента → PDF на 1 сторінку (з перевіркою чисел)
```

Ключові рішення:

1. **Код робить усю роботу з даними, агент лише інтерпретує.** Слабка модель не пише
   HTTP-запити й статистику з нуля. Вона викликає 2–3 команди й читає підсумок, де числа
   вже округлені так, як їх варто цитувати. Кожен висновок супроводжує вердикт
   (growing / declining / flat / unclear), рівень довіри та список причин «чому».
2. **Одна тема — один об'єкт Wikidata.** Назву статті в кожній мові бере з sitelinks
   Wikidata, тож порівнюються еквівалентні статті, а не вгадані агентом назви. Якщо в мові
   статті немає, це повідомляється як окремий висновок, а не мовчки пропускається.
   Приклад: у польській Вікіпедії немає статті про інтервальне голодування. Для таких
   випадків є явні «статті-замінники» (`pl:Назва`); вони позначаються, а довіра до них
   знижується.
3. **Перегляди редиректів додаються.** Інакше перейменування статті виглядало б як обвал
   інтересу.
4. **Нормалізація на весь мовний розділ.** Загальний трафік Вікіпедії падає на 10–30% на
   рік (пошукові сніпети, AI-відповіді). Без нормалізації майже будь-яка тема «падає».
   Основна метрика — частка статті від усіх переглядів розділу (views per million), сирі
   перегляди показано поруч.
5. **Статистика, стійка до новин.** Нахил Сена (Sen's slope) і тест Манна-Кендалла з
   поправкою Yue-Wang на автокореляцію. Сплески виявляються через robust z-score
   (median/MAD). Піки, що повторюються щороку (вересень для астрономії), позначаються як
   сезонність, а не новини. Порівняння «останні 12 міс. vs попередні 12» прибирає
   сезонність.
6. **Прозора довіра.** До 5 балів: довжина ряду, значущість, узгодженість метрик, стійкість
   до сплесків, обсяг трафіку. Кожен бал має текстову причину, яку агент цитує.
7. **Ранжування з вагами користувача.** «Для нас важливіший розмір аудиторії» → `--weights volume=0.6,...`.
   Складники (growth / volume / trust) видно завжди.
8. **Звіт не може містити вигаданих чисел.** Графік, таблиця й застереження генерує код.
   Агент пише лише заголовок, висновок, рекомендацію й наступні кроки. Кожне число в цьому
   тексті звіряється з `analysis.json` (з урахуванням округлень, `1,234` vs `1 234`,
   `12K`). Якщо число не знайдено, PDF не створюється, і агент бачить, які саме числа
   прибрати.
9. **Повторні й пов'язані запити дешеві.** SQLite-кеш: дані за завершені місяці кешуються
   назавжди, решта має TTL. «Додай словацьку» довантажує лише нові ряди.
   `wpv show` повертає підсумок без мережі.

## Перевірка на дешевій моделі: з навичкою vs без

**Як тестувалось.** Claude Haiku 4.5 (`claude-haiku-4-5-20251001`) у headless Claude Code
(`claude -p`). Кожен прогін іде в чистій папці, де підключена лише ця навичка
([`evals/run_eval.py`](wikipedia-pageviews/evals/run_eval.py)). Baseline — та сама модель
без навички, але з доступом до Bash, WebFetch і WebSearch. Сценаріїв 5: три приклади із
завдання, повторний запит зі зміною критеріїв ранжування та англомовний запит
([`evals/evals.json`](wikipedia-pageviews/evals/evals.json)). Кожен сценарій прогнано по
2 рази в кожній конфігурації. Грейдер детермінований
([`evals/grade.py`](wikipedia-pageviews/evals/grade.py)): перевіряє транскрипт, відповідь і
артефакти. Головна перевірка — «кожне число у відповіді є в `analysis.json`».

| Ітерація 2 (20 прогонів) | З навичкою | Без навички |
|---|---|---|
| Пройдено перевірок | **99% ± 5%** | 29% ± 11% |
| Час на сценарій | **35 с** ± 7 | 90 с ± 67 |
| Вартість на сценарій | **$0.055** (макс. $0.09) | $0.33 (макс. $1.07) |
| Токени | **122K** | 331K |

Деталі по кожному прогону: [`evals/results/`](wikipedia-pageviews/evals/results/).

**Що робить Haiku без навички** (з транскриптів):
- **Не отримує даних про перегляди.** В ітерації 1, де не було WebSearch, він просив
  дозволу на пошук і радив користувачу самому відкрити pageviews.toolforge.org.
  З WebSearch/WebFetch він читає самі статті Вікіпедії.
- **Підміняє питання.** Про медитацію японською і корейською він порівнював кількість
  розділів і виносок у статтях замість інтересу читачів. Про англійську він вставив у звіт
  ринкову статистику з вебу («800 млн учнів, 10% CAGR»), не пов'язану з Вікіпедією.
- **Помиляється в суті.** «Шахи»: німецьку поставив першою за розміром аудиторії,
  спираючись на загальну статистику розділу. Насправді статтю про шахи найбільше читають
  іспанською (медіана 21 862 проти 14 932 перегляди на місяць).
- **Коли сам викликає API через curl, пропускає нормалізацію.** Для астрономії він
  порахував «−46% за 6 місяців» по сирих переглядах, тобто змішав падіння інтересу із
  загальним падінням трафіку Вікіпедії (−25%/рік в українській) і з сезонністю.
- **Дорожчає без результату.** Один прогін витратив 6 хвилин і $0.86 (35 запитів WebFetch
  і субагент) і так і не отримав жодного числа переглядів.

**Що робить Haiku з навичкою:** 2–4 виклики CLI (`resolve` → `analyze` → за потреби `report`).
- **Помічає відсутні статті.** Що в польській Вікіпедії немає статті про інтервальне
  голодування, Haiku помітив у всіх прогонах, сказав про це й запропонував замінник.
- **Відповідає на «чи можна довіряти».** Цитує p-value, рівень довіри й причини:
  довжину ряду, сплески, сезонність (вересень для астрономії).
- **Виконує повторні запити без зайвих кроків.** «Додай іспанську та італійську, нам
  важливіший розмір аудиторії» дає один перезапуск з `--weights volume=0.8,...`.
  Дані за вже завантажені мови беруться з кешу.
- **Сам виправляє числа у звіті.** У 2 з 5 прогонів зі звітом перевірка відхилила
  першу версію тексту (числа «340», «155», яких немає в даних). Haiku викликав
  `wpv show`, виправив текст, і PDF зібрався.

**Що змінилося між ітераціями** (ітерація 1: 94% з навичкою → ітерація 2: 99%):
- Haiku сам рахував похідні числа й помилявся: «на 56% більше», а правильно 46%. У
  підсумок додано готовий блок HIGHLIGHTS. Перевірка тепер приймає коректні попарні
  порівняння (≈50%, 2.5×) і далі відхиляє хибні.
- Відповідь не пояснювала, що тренд рахується на частці від трафіку розділу. Це стало
  обов'язковим рядком відповіді в `SKILL.md`.
- Haiku аналізував ширше поняття («голодування загалом») як окрему тему і вигадав, що
  потрібна тема «входить» у цю статтю. `SKILL.md` тепер направляє на явні
  статті-замінники (вони позначаються й знижують довіру) і забороняє твердження про
  вміст статей.
- Грейдер мав хибні спрацювання: числа з шляхів до файлів, вибір не того `analysis.json`,
  надто вузький regex. Їх виправлено, і обидві ітерації переоцінено тим самим грейдером.

Приклади відповідей, графіків і PDF, згенерованих Haiku: [`examples/`](wikipedia-pageviews/examples/).

## Обмеження (свідомі рішення v1)

- **Перегляди ≠ попит.** Інтерес до статті не означає готовність платити. Навичка
  допомагає обрати, що перевіряти далі, і прямо пише про це у висновках і в PDF.
- **Мовний розділ ≠ країна.** Іспанську Вікіпедію читають в Іспанії, Мексиці, США, а
  англійську читає весь світ.
- **Одна стаття — це наближення теми.** Кластер статей можна задати вручну
  (`Label=Q1,Q2,Q3`), автоматичного розширення поки немає (див. план розвитку).
- **Людський трафік визначається евристично.** Залишки ботів проявляються як сплески;
  вони позначаються, і висновок перевіряється без них.
- Фіксовані підписи PDF є українською та англійською. Текст агента може бути будь-якою
  мовою: шрифт DejaVu покриває кирилицю, латиницю й грецьку, але не CJK. Для
  японської чи корейської зараз варто писати текст звіту англійською.

## Як розвивати далі

Порядок визначається тим, що найбільше обмежує якість висновків зараз.

1. **Кластери тем замість однієї статті.** Команда `wpv expand Q333`, яка пропонує
   суміжні статті через зв'язки Wikidata (`P279` subclass of, `P361` part of) і найчастіші
   переходи з [Clickstream](https://meta.wikimedia.org/wiki/Research:Wikipedia_clickstream).
   Агент показує список, користувач підтверджує, у звіті видно внесок кожної статті.
   Тоді «астрономія» означатиме тему, а не одну статтю.
2. **Розмір ринку.** Додати кількість носіїв мови та розподіл читачів розділу за країнами
   ([pageviews by country](https://doc.wikimedia.org/generated-data-platform/aqs/analytics-api/reference/page-views.html)),
   щоб ранжування враховувало не лише обсяг переглядів, а й охоплення.
3. **Більші обсяги.** Для сотень статей або мов REST API повільний (1 запит на статтю ×
   мову). Наступний крок — місячні дампи [pageview complete](https://dumps.wikimedia.org/other/pageview_complete/)
   у DuckDB/Parquet із локальним індексом за QID. Той самий `analysis.json` на виході,
   тож агент і звіти не змінюються. SQLite-кеш уже ізолює мережевий шар.
4. **Прогноз і детекція зламів тренду.** Сезонна декомпозиція (STL) для рядів понад
   3 роки та пошук точок зміни (change-point), щоб відповідати на питання «коли почалося
   зростання і чи триває воно».
5. **Кросперевірка сигналу.** Google Trends і пошукові підказки магазинів застосунків як
   другий незалежний індикатор. Висновок «зростає» з високою довірою лише тоді, коли
   джерела узгоджуються.
6. **Evals як регресійні тести.** Розширити набір до 15–20 сценаріїв (зокрема
   «пастки»: неоднозначні назви, статті, створені посеред періоду, мови без статті)
   і ганяти їх у CI на кожну зміну `SKILL.md`. Опис навички оптимізувати
   `run_loop` з skill-creator, щоб вона точніше вмикалася за релевантними запитами.

## Як я використовував AI і перевіряв його результат

Код, `SKILL.md` і evals написані разом із Claude Code (Opus). Спершу ми зафіксували
всі проєктні рішення в режимі інтерв'ю, потім працювали за процесом
[skill-creator](https://github.com/anthropics/skills): чернетка, прогони на Haiku,
оцінка, правки. Я не приймав результат на віру:

- **Статистику перевірено незалежною бібліотекою.** `evals/crosscheck.py` перераховує
  нахил Сена й p-value через `pymannkendall`, а сирі числа завантажує окремим кодом
  напряму з API. На цій звірці знайшлася неточність у поправці на автокореляцію:
  AI-версія застосовувала поправку AR(1) з порогом значущості, а стандартна
  (Yue & Wang, 2004) цього не робить. Замінено, і тепер значення збігаються до 4-го знака.
- **Тести на синтетичних рядах з відомою відповіддю** (тренд, шум, сплеск, сезонність,
  автокорельоване блукання) та офлайн-тести на записаних відповідях API: `uv run pytest`.
- **Ручна перевірка графіків і PDF.** Так знайдено, що щорічні вересневі піки для
  астрономії визначалися як «новинні сплески». Тепер вони позначаються як сезонність.
- **Перевірку чисел у PDF протестовано на вигаданих числах.** Перша версія мала допуск 2%
  і пропускала «2030» як «≈2027». Тепер число має бути саме округленням значення з даних.
- **Кожна зміна `SKILL.md` проходила через evals на Haiku** (див. вище). Тексти
  відповідей я також читав вручну, бо грейдер на регулярних виразах бачить не все.
  Частина «провалів» ітерації 2 виявилася помилками самого грейдера, а не навички.
